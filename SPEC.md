# NutriOS — Landing Page Implementation Specification

**Version:** 1.0  
**Project:** NutriOS — Personal Nutrition OS  
**Type:** Responsive Product Landing Page  
**Framework:** React JS  
**Language:** Russian (ru-RU)  
**Target:** Desktop / Tablet / Mobile  
**Product stage:** Concept / Pre-launch (default)  
**Priority:** MVP Landing Page  
**Implementation owner:** AI Coding Agent

---

## 0. Project Context & Constraints

### Product context

NutriOS — персональный wellness/education assistant для планирования питания с учётом целей, пищевых предпочтений, ограничений, истории выбора и повседневного контекста пользователя.

Продукт помогает организовывать питание, а не лечить заболевания, назначать медицинские диеты или гарантировать определённые результаты.

### Implementation assumptions

1. Использовать React и существующую архитектуру проекта.
2. Если проект ещё не создан, использовать React + Vite + JavaScript (JSX).
3. При наличии TypeScript сохранить TypeScript.
4. Не заменять существующие зависимости, стили и маршрутизацию без необходимости.
5. Лендинг должен работать без backend.
6. Все демонстрационные данные должны быть локальными и детерминированными.
7. Не подключать AI API для демонстрации.
8. Не создавать фиктивные регистрацию, авторизацию, оплату или сбор заявок.
9. Не использовать непроверенные заявления о продукте.
10. Не придумывать медицинские рекомендации или персональные лечебные планы.

**Scope:** публичный лендинг с интерактивным App Preview.

**Out of scope:** полноценное приложение, серверная персонализация, аутентификация, обработка персональных данных, реальные медицинские или нутриционные рекомендации, платежи.

# 1. Цель страницы

## 1.1 Primary Goal

Объяснить потенциальному пользователю, что такое NutriOS, какую повседневную проблему решает продукт и почему он отличается от обычного планировщика питания.

Посетитель должен за первые 5–10 секунд понять:

- NutriOS помогает планировать питание.
- Планирование учитывает личный и бытовой контекст.
- Пользователь может менять предложенный план.
- NutriOS не является медицинским сервисом.

## 1.2 Secondary Goals

- Показать архитектуру будущего приложения.
- Продемонстрировать сценарий персонализации и изменения плана.
- Сформировать доверие к подходу продукта.
- Проверить интерес к концепции.
- Подготовить основу для последующего подключения регистрации или waitlist.

## 1.3 Success Criteria

Пользователь может:

1. Понять главную ценность без чтения всей страницы.
2. Перейти к демонстрации продукта.
3. Увидеть пример недельного плана.
4. Изменить демонстрационное блюдо.
5. Найти информацию об ограничениях сервиса.
6. Использовать страницу на мобильном устройстве.

## 1.4 Conversion Strategy

Поддержать три режима CTA через конфигурацию:

| Mode | Primary CTA | Destination |
|---|---|---|
| concept (default) | Посмотреть демо | #app-preview |
| waitlist | Получить ранний доступ | Реальная форма регистрации интереса |
| live | Создать свой план | Существующий маршрут onboarding |

Режим waitlist допускается только при наличии работающего endpoint, необходимой политики конфиденциальности и обработки согласия.

Режим live — только при наличии реального onboarding.

**Запрещено:** показывать успешную отправку формы без фактического подтверждения со стороны backend.

## 3.9 FAQSection

### Question 1

**NutriOS — приложение для похудения?**

NutriOS создан для организации повседневного питания. Его основная задача — помогать планировать меню с учётом предпочтений и обстоятельств, а не обещать изменение веса.

### Question 2

**Нужно ли считать калории?**

Основной сценарий NutriOS построен вокруг планирования блюд и личных предпочтений. Обязательный подсчёт калорий не является частью концепции.

### Question 3

**Можно ли исключать определённые продукты?**

В концепции продукта предусмотрены настройки пищевых предпочтений и исключений. При пищевой аллергии необходимо самостоятельно проверять состав и маркировку продуктов.

### Question 4

**Можно ли менять предложенный план?**

Да, гибкое изменение меню — один из основных принципов NutriOS. Возможность замены можно попробовать в интерактивном демо.

### Question 5

**NutriOS заменяет диетолога или врача?**

Нет. NutriOS не предназначен для диагностики, лечения или назначения лечебного питания.

### Question 6

**NutriOS уже доступен?**

В текущей версии лендинга представлен концепт продукта и интерактивное демо. Доступность приложения будет объявлена отдельно.

При переходе в live mode обновить последний ответ на фактически подтверждённую информацию.

### Interaction

- Accordion.
- По умолчанию все вопросы закрыты.
- Открытие и закрытие по click / Enter / Space.
- Поддержка нескольких открытых ответов допустима.
- Анимация раскрытия не обязательна.

# 4. UX-логика

## 4.1 User Journey

**Entry → Understanding → Exploration → Demo Interaction → CTA**

### Entry

Пользователь видит оффер и макет приложения.

### Understanding

Пользователь знакомится с проблемой, преимуществами и принципом работы.

### Exploration

Пользователь изучает ключевые возможности.

### Demo Interaction

Пользователь выбирает день и заменяет блюдо в локальном preview.

### CTA

Пользователь переходит к демонстрации или, после подключения реальной интеграции, к onboarding / waitlist.

## 4.2 Navigation Behavior

- Все anchor-ссылки ведут к существующим секциям.
- Прокрутка плавная, если пользователь не включил reduced motion.
- Sticky header не перекрывает заголовки разделов.
- Mobile menu закрывается при выборе раздела.
- Mobile menu закрывается по Escape.
- При закрытии меню фокус возвращается на кнопку открытия, если закрытие инициировано Escape.
- При переходе к якорю должна сохраняться корректная клавиатурная навигация.

## 4.3 Interactive Preview State

React local state:

- `selectedDay`
- `viewMode`
- `mealOverrides`

Допустимые значения:

- selectedDay: mon / tue / wed / thu / fri / sat / sun.
- viewMode: day / week.
- mealOverrides: объект с заменами для отдельных приёмов пищи.

### State Transition

Initial:
- selectedDay = mon
- viewMode = week
- mealOverrides = {}

Day selected:
- Обновить selectedDay.
- В режиме day отобразить блюда выбранного дня.
- В режиме week визуально выделить выбранный день.

Replace:
- Найти целевой demo meal.
- Заменить на заранее заданную альтернативу.
- Не менять другие дни или блюда.
- Объявить изменение через доступную live-region.

Reset:
- Очистить mealOverrides.
- Вернуть выбранный день и режим к начальному состоянию.

## 4.4 CTA Behavior

Режим CTA должен задаваться централизованно.

**Concept mode:**
- Все основные CTA ведут к App Preview.
- Никаких форм сбора данных.

**Waitlist mode:**
- Только реальный endpoint.
- Валидация email.
- Явное информирование об обработке данных.
- Согласие, когда оно необходимо.
- Loading, success и error states.
- Защита от повторной отправки.
- Никакого ложного success.

**Live mode:**
- CTA ведёт к существующему onboarding route.
- Не создавать фиктивную страницу регистрации.

## 4.5 General Interaction Rules

- Все активные элементы должны иметь видимый результат действия.
- Не делать неактивные элементы похожими на доступные ссылки.
- Hover не должен быть единственным способом получения информации.
- Любая анимация должна быть необязательной.
- Состояния интерфейса должны быть предсказуемыми.

# 5. Visual Direction

## 5.1 Brand Personality

- Структурированная сетка.
- Пространство между элементами.
- Скруглённые карточки.
- Сдержанные тени.
- Лаконичные иконки.
- Минимум декоративных эффектов.

## 5.3 Color Tokens

Предлагаемая стартовая палитра:

| Token | Value |
|---|---|
| background | #F7F9F6 |
| surface | #FFFFFF |
| primary | #245A46 |
| primary-light | #E2F0E7 |
| heading | #172820 |
| text | #34443B |
| muted | #637168 |
| border | #DCE5DD |
| accent-soft | #F1E9D9 |
| danger | #A12D36 |

Цвета необходимо проверить на соответствие требованиям контрастности.

Primary применяется для основных CTA, активных элементов и важных визуальных акцентов.

## 5.4 Typography

- Современный sans-serif.
- Возможные направления: Inter / Manrope / system UI.
- Приоритет — читабельность кириллицы.
- Не загружать несколько тяжёлых font families.
- H1: примерно 40–64 px на desktop, 32–40 px на mobile.
- H2: 28–44 px.
- Body: 16–18 px.
- Secondary text: 14–16 px.
- Использовать responsive `clamp()` при необходимости.

## 5.5 Spacing & Layout

- Base spacing unit: 4 или 8 px.
- Container max-width: 1200 px.
- Desktop section spacing: 80–120 px.
- Mobile section spacing: 48–72 px.
- Card radius: 16–24 px.
- Button radius: 10–14 px.
- Базовые интерактивные области: желательно не менее 44 × 44 px.

## 5.6 Responsive Breakpoints

Рекомендуемые ориентиры:

- Mobile: до 767 px.
- Tablet: 768–1023 px.
- Desktop: от 1024 px.

Адаптация определяется содержимым, а не только фиксированными breakpoint.

На ширине 320 px не допускается горизонтальная прокрутка страницы.

## 5.7 Imagery

- Приоритет — качественные изображения реальных продуктов питания и интерфейса.
- Не использовать изображения «до/после».
- Не акцентировать внимание на весах, измерении талии и медицинском оборудовании.
- Фотографии блюд должны выглядеть естественно.
- Не использовать тяжёлые фоновые видеоролики.
- В App Preview допустимы CSS-иллюстрации и оптимизированные локальные изображения.

## 5.8 Motion

- Hover transitions: примерно 150–200 ms.
- UI state transitions: примерно 150–250 ms.
- Без навязчивого параллакса.
- Без автоматически запускаемых анимаций, отвлекающих от контента.
- Уважать `prefers-reduced-motion`.

# 7. Accessibility Requirements

**Target: WCAG 2.2 AA.**

Reference: https://www.w3.org/TR/WCAG22/

## 7.1 Semantics

- Единственный H1.
- Логичная иерархия заголовков.
- Основные landmark-элементы.
- `lang="ru"` для русскоязычной страницы.
- Декоративные изображения скрыты от screen reader.
- Содержательные изображения имеют полезный alt.

## 7.2 Keyboard Navigation

- Все действия доступны с клавиатуры.
- Tab order соответствует визуальной и смысловой последовательности.
- Видимый focus indicator.
- Отсутствуют keyboard traps.
- Mobile navigation управляется с клавиатуры.
- Escape закрывает мобильное меню, если оно открыто.
- Интерактивные элементы App Preview доступны без мыши.

## 7.3 Contrast

- Обычный текст: минимум 4.5:1.
- Крупный текст: минимум 3:1.
- Значимые графические элементы и границы UI: минимум 3:1, где применимо.
- Состояния не передаются исключительно цветом.

## 7.4 Forms and Controls

Если используются формы:

- Каждое поле имеет label.
- Обязательные поля обозначены.
- Ошибки описаны текстом.
- Ошибки связаны с соответствующим полем.
- Успех и ошибки доступны screen reader.
- Нельзя полагаться исключительно на placeholder.

## 7.5 App Preview

- Выбор дня должен иметь понятное активное состояние.
- Переключатель режимов должен иметь доступное название и состояние.
- Кнопка Replace уточняет, какое блюдо заменяется.
- Изменения содержимого объявляются через `aria-live="polite"` или эквивалентный доступный механизм.
- Reset доступен с клавиатуры.

## 7.6 Responsive Accessibility

- Масштабирование до 200% без потери функций.
- Проверка reflow при ширине viewport, эквивалентной 320 CSS px.
- Достаточные размеры touch targets.
- Нет информации, доступной только при hover.
- Reduced motion поддерживается.

# 8. Performance Requirements

## 8.1 Core Web Vitals

Production targets, измеряемые на 75-м процентиле реальных посещений:

| Metric | Target |
|---|---|
| LCP | ≤ 2.5 s |
| INP | ≤ 200 ms |
| CLS | ≤ 0.1 |

Reference: https://web.dev/articles/vitals

## 8.2 Lighthouse

Целевые показатели в согласованном мобильном профиле проверки:

- Performance: ≥ 90.
- Accessibility: ≥ 90 (при обязательной ручной проверке WCAG).
- Best Practices: ≥ 90.
- SEO: ≥ 90.

Lighthouse является лабораторным инструментом и не заменяет измерение полевых Core Web Vitals.

## 8.3 Assets

- Изображения: AVIF/WebP при наличии.
- Подходящие responsive sizes.
- Явные размеры изображений для предотвращения layout shift.
- Lazy-loading изображений ниже первого экрана.
- Не применять lazy loading к критичному hero-изображению.
- Не загружать тяжёлые изображения ради мелких карточек.
- Использовать SVG для простых иконок.

## 8.4 JavaScript

- Минимум зависимостей.
- Не использовать тяжёлые animation libraries без необходимости.
- Не создавать лишние таймеры или постоянные обновления state.
- Интерактивное демо должно быть быстрым и предсказуемым.
- По возможности не включать крупные сторонние библиотеки в initial bundle.

## 8.5 Fonts

- Минимальное количество начертаний.
- WOFF2 или системные шрифты.
- `font-display: swap` для загружаемых шрифтов.
- Избегать layout shift от поздней загрузки шрифтов.

## 8.6 SEO & Metadata

- Уникальный title.
- Meta description.
- Корректная semantic heading hierarchy.
- Open Graph title / description.
- Open Graph image — при наличии реального файла.
- Canonical URL — после определения production domain.
- Favicon — при наличии утверждённого asset.

Suggested title:
